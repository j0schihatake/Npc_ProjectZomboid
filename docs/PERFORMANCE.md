# Проверка производительности

Требование пользователя: доработки не должны заметно ухудшать производительность.
Автотесты ограничений не заменяют замеры в игре. Замеры FPS/времени кадра
для 0.4.4 пока не выполнены; отсутствие ухудшения не подтверждено.

## Проверка реакций 0.4.40 и подготовленная оптимизация

В текущем console.txt SmoothFrames записал 10.8 мс для обработчика
`PersonalKnox/Reactions.lua`, EveryOneMinute, кадр 50 после загрузки мира.
Это единичный ранний вызов; прогрев Java и загрузка сцены не исключены.
Он не доказывает постоянную просадку и не заменяет сравнение повторов.
В продолжении того же журнала есть ещё 10.9 мс (кадр 566) и 9.0 мс (кадр 723).
Профилировщик показывает медленные вызовы, а не все опросы; среднее время
и p95 из этих трёх строк вычислять некорректно.

В отдельной ветке `reaction-performance` подготовлен общий снимок координат
видимых кандидатов на один опрос: не более 24 × 2 чтений координат целей
и 4 × 2 чтений координат NPC. Числа хранятся в двух переиспользуемых массивах
максимум по 24 элемента; ссылки на мировые объекты в них не сохраняются.
Повторный опрос полностью обновляет используемые элементы, старый хвост
не участвует при уменьшении списка целей.

В одной и той же Lua-сцене (4 NPC, 24 кандидата, ближайшая цель не первая):
прежний код выполняет 200 чтений координат NPC и 200 чтений координат целей;
подготовленный код — 8 и 48. Проверка нового лимита падает на старом коде.
Число проверок CanSee остаётся не больше 96; частота, дальность, выбор цели,
порядок ротации, приоритеты и паузы Java-директора не меняются.

Это сокращение числа вызовов Lua–Java, не измерение FPS. Оптимизация ещё не
установлена в работающую игру, время обработчика после неё не измерено.

## Подготовленное ограничение общего поиска отряда

В текущем журнале обработчик контекстного меню PersonalKnox отмечен в том числе
на 27.9 и 113.4 мс. Причина каждого пика не изолирована: строка профилировщика
не доказывает, что всё время занимает поиск отряда.

Проверка кода нашла, что общий `Client.roster` имел предел площади 17×17,
но не числа движущихся объектов на этих клетках. Этот callback используется
также некоторыми фоновыми функциями NPC, поэтому утверждение ниже о единственном
регулярном обходе только в Reactions для текущей 0.4.40 уже не является полным.

В ветке `reaction-performance` дополнительный поиск ограничен 512 объектами
при прежних максимум 289 клетках. Все NPC, уже полученные из выбранного отряда
и списка работников убежища, сохраняются; поиск не отменяет их членство или
приказы. В насыщенной сцене неизвестные этому списку близкие NPC за пределом
бюджета могут не попасть в этот конкретный результат — это ограничение
вспомогательного обнаружения, а не численности самого отряда.

Координаты игрока читаются один раз (3 getter-вызова вместо до 325 при полном
обходе). Тесты проверяют насыщенную и разреженную сцену, сохранение известных
членов, исключение посторонних и отсутствие дубликатов. Старый код нарушает
новый лимит объектов. Время меню после изменения в игре пока не измерено.

В работающем запуске повторяется `PersonalKnox Chatter error: Object tried to call nil`.
Такой запуск не считать чистой проверкой версии. Незавершённые изменения NPC-ID
в основной рабочей копии сохранены отдельно от этой оптимизации; их результат
нужно проверять новым запуском после завершения соответствующей правки.

## Ограничения по коду

- Реакции: одно событие EveryOneMinute; максимум 169 клеток, 256 движущихся
  объектов, 24 сохранённых цели, 8 найденных NPC и 4 обработанных NPC за опрос.
- Видимость: не больше 4 × 24 проверок; нет полного списка зомби мира.
- Направления 0.4.4: ближайшая цель выбирается в прежнем цикле видимости.
  Новый обход или обработчик кадров не добавляется; расчёт сектора на Java
  выполняется только для уже разрешённой к произнесению фразы react_zombies.
- При отключённых реакциях нет опроса мира. Состояния Java ограничены 128 NPC.
  SQLite используется при сборке; в игре реплики читаются из ресурса JAR.
- Диагностика доступных Lua-классов: одна строка на загрузку мира без обхода.
- Ограничения снабжения и баррикадирования проверяются отдельными Lua-тестами;
  их реальная стоимость и одновременная работа ещё требуют замеров.

## Границы Java и Lua

Требование пользователя: большая часть доработок — в Java, Lua остаётся тонким
адаптером. Сейчас так и разделено:

- Java: приоритеты и паузы реплик, выбор фразы из SQLite-экспорта, расписание,
  план снабжения, статусы баррикад, политика выбора оружия, сектор угрозы.
- Lua: подписка на события, доступ к клеткам/объектам/инвентарю, меню Viewpoint,
  `ModData` и вызовы существующих команд Knox.

Единственный регулярный обход мира остался в Lua — `Reactions.sample` (169 клеток,
256 объектов, до 4 NPC раз в минуту). Он ограничен, но каждый объект пересекает
границу Lua↔Java. Перенос опроса в Java запланирован в ROADMAP; до него нужны
игровые классы в classpath сборки, проверка моста объектов ZombieBuddy и замеры
до/после. Меню и события остаются в Lua: это разовые вызовы, не горячий путь.

## Сравнение в игре

1. Дождаться завершения установки Steam; не совмещать замер с загрузкой/установкой
   модов. Не менять настройки камеры, графики, лимит FPS, время и погоду между
   сравнениями. Зафиксировать версии и список всех модов.
2. На независимых копиях одного исходного мира сравнить 0.4.3 и 0.4.4. Первое
   прохождение участка использовать для прогрева загрузки и Java; его не считать.
3. Проверить три одинаковые сцены: спокойная база; несколько следующих NPC;
   бой отряда с толпой. Отдельно проверить движение через плотный город с Viewpoint.
4. Сделать не менее трёх повторов каждой сцены, чередуя версии. Сравнить медиану
   FPS, 95-й процентиль времени кадра и заметные паузы; зафиксировать число NPC
   и зомби. В бою полная повторяемость невозможна, поэтому один прогон недостаточен.
5. Если разница превышает естественный разброс повторов, найти причину до выпуска.
   При ограничителе FPS одинаковый счётчик не доказывает одинаковый запас CPU/GPU.

Запись результата: версия/commit, мир, моды, настройки, сцена, три измерения,
медиана FPS, p95 времени кадра, паузы и ошибки журнала. Пока нет таких данных,
указывать только подтверждённые лимиты, не обещать нулевое влияние на FPS.
