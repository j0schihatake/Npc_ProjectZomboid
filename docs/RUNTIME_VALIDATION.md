# Что доказывает журнал запуска

Сообщение Java содержит версию ядра, сообщение Client — версию Lua-дополнения.
Java сообщает версию собранного ядра. Для Lua `Version` один раз получает
объявленную версию через игровой `getModInfoByID():getModVersion()` в момент
загрузки окружения. Последующие чтения не заменяют её поздней версией на диске.
Так обновления только Lua не требуют вручную менять номер в сообщении Client.
`check_lua.py` проверяет выбор метаданных, кэширование и неизвестный результат
при отсутствии API. Не менять файлы работающей игры ради маркера.

`python3 tools/check_run.py --expect 0.4.53` проверяет Java и Lua 0.4.53.
Если при обновлении изменялась только Lua, обе ожидаемые версии указываются явно:
`python3 tools/check_run.py --expect 0.4.53 --expect-lua 0.4.54`.
Не подбирать эти аргументы лишь ради PASS: Java-версия должна соответствовать
собранному ядру, Lua-версия — установленному выпуску адаптеров.

Старое сообщение «Lua addon loaded» остаётся распознаваемым как факт загрузки,
но его версия считается неподтверждённой. Несовпадение версии Lua, отсутствие
её загрузки после последнего запуска ядра и собственные ошибки дают ненулевой
код завершения проверки. Правильная Java с неверной Lua не считается PASS.

Даже PASS подтверждает только указанные сообщения загрузки и отсутствие
распознанных ошибок PersonalKnox в этом журнале. Он не проверяет контрольные
суммы всех файлов или соответствие исходников объявлению версии. Пакетная
метаинформация не обнаружит подмену файла после её чтения. Состояние чужих
модов, завершение работ NPC, анимации,
сохранение/загрузку мира или FPS. Эти сценарии проверяются отдельно; счётчики
`probe`, `care`, `upkeep` служат подсказками и сами по себе не доказывают успех.
