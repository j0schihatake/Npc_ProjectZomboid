# Запуск для агента DeepSeek

Использовать существующий `tools/launch_dev.sh` в PersonalKnox-dev. Этот launcher
теперь по умолчанию проходит весь dev-сценарий, а не заканчивает проверку на меню.

```bash
cd /home/j0schi/Zomboid/PersonalKnox-dev
./tools/launch_dev.sh
```

Параметры уже вписаны в DEFAULT_ARGS существующего shell-скрипта:
`--restart --build --detach --no-debug --nosteam`. Для обычного запуска их вводить
не нужно. Единственный флаг `--menu-only` сохраняет эти параметры, но отключает
сценарий и оставляет игру в главном меню. Если передан другой набор явных
аргументов, используются они — это позволяет проверить готовый JAR без
пересборки или выполнить только `--status`.

`--restart` завершает только свою записанную dev-игру через SIGTERM и ждёт выхода.
Нужное состояние dev-мира заранее сохранить через меню; SIGTERM не гарантирует
сохранение. `--build` собирает выбранные наши проекты. `--no-debug` и `--nosteam`
сохранены для совместимости с прежней командой агента; их можно не указывать.
Существующий `tools/launch_test.sh` вызывает этот же launcher с restart/build/detach.
Он больше не заменяет обычный `~/Zomboid/mods/default.txt` файлом из старого backup.

Что выполняется автоматически:

1. Подготовка отдельного cachedir `~/Zomboid-dev/PersonalKnox`, ссылки на установленные
   Workshop-моды, выбор ZombieBuddy/Viewpoint/Knox/KnoxRU/PersonalKnox и служебного
   dev-сценария. Создаётся штатный `mods/reset-mods-42_00.txt`, без которого первый
   запуск B42 очищает подготовленные галочки модов.
2. Проверка доверия нашим сборкам и обновление разрешения текущего хеша JAR в штатном
   кэше ZombieBuddy. На новом профиле один раз добавить `--trust-local-builds`;
   старый флаг `--approve-own` остаётся его псевдонимом. Последующие пересборки из
   того же доверенного каталога не требуют повторного флага. Чужие разрешения
   сохраняются, перед изменением создаётся backup.
3. Выбор закрытого Sandbox-сохранения с живым игроком и доступными картами. Сначала
   пробуется последнее, затем остальные. Создаётся новая независимая копия
   `PersonalKnox-scenario-<nonce>` в dev-cache. Оригинал не изменяется; его хеши
   проверяются до/после. Копия получает текущий список модов.
4. Загрузка копии через штатный Continue. Служебный Java agent подтверждает экран
   «нажмите, чтобы начать» только в этом мире; проверки готовности ресурсов остаются.
5. Закрытие инвентаря, добычи, подсказок инвентаря и приветственного SurvivalGuide,
   включая окна, появившиеся чуть позже. После сценария инвентарь можно открыть снова.
6. Если появляется окно генерации Knox: Generate один раз, ожидание isGenerated,
   проверка ненулевого числа выживших, штатное Place NPCs & Close. Повторной генерации
   при отсутствии окна нет.
7. По умолчанию запускается сценарий `own-npc`: создаёт одного нашего NPC на
   свободной загруженной клетке рядом с игроком, с приказом HOLD. Требует отдельное
   от игрока тело в списках клетки/квадрата и активную модель три тика подряд.
   Отсутствующее тело даёт FAIL. Snapshot пишется в ModData перед saveGame() копии.
   Старый сценарий без создания NPC доступен явно через `--scenario smoke`.
   F10 в игре вызывает тот же Java API `ownCreateCompanion(player)` один раз.

В 0.9.38 создание подтверждено в реальном мире и визуально в FPS. Видимость в
обычном виде, поведение, восстановление после загрузки и влияние на FPS требуют
отдельной проверки. Knox пока остаётся зависимостью загрузки, но наличие его
отряда для тестового создания нашего NPC не требуется.

`--detach` отделяет процесс игры, но **ожидает результат сценария**. Успех — строка
`OK: ...` и код 0; ошибка — код 1, таймаут — 2. Старый успешный JSON не засчитывается:
результат связан с nonce и миром текущего запуска. По таймауту игра не убивается,
остаётся доступной для диагностики. Это проверка запуска, API, тиков и сохранения,
а не гарантия исправности всех анимаций/NPC или FPS.

```bash
./tools/launch_dev.sh --status
./tools/launch_dev.sh --scenario-save /absolute/path/to/Sandbox/world --detach
./tools/launch_dev.sh --scenario-timeout 1200 --detach
./tools/launch_dev.sh --profile full --detach
./tools/launch_dev.sh --menu-only             # Подготовить/перезапустить и остаться в меню
./tools/launch_dev.sh --prepare-only         # Подготовить профиль без запуска
./tools/launch_dev.sh --dry-run              # Показать план без записей
```

Длительность проверки в мире: `--scenario-seconds 10`, общий предел ожидания:
`--scenario-timeout 600`. Для full сохраняется порядок карт из обычного профиля.
Если явному `--scenario-save` не хватает карт, launcher сообщает об этом до запуска;
не следует вручную обходить окно ошибки сохранения.

Журналы и результат: `console.txt`, `launch-logs/…log`, `dev-launch.json`,
`dev-scenario.json`, `Lua/PersonalKnox-dev-scenario-result.json` внутри dev-cache.
`--status` проверяет живой PID/start-time, текущий лог и результат именно этого
запуска. Успешная фаза — `scenario_ok`. Просто наличие PID не доказывает вход в мир.

PersonalWorldGen остаётся отдельным проектом. Профили worldgen/both доступны только
после появления его игрового B42-пакета; launcher не подменяет его NPC-модом.
Нормальные сохранения, набор модов и опции в `~/Zomboid` не перезаписываются.
Публикация и отправка материалов не выполняются.

## Обновление launcher и отдельный JAR harness

Не восстанавливать файлы launcher и его инструкцию через `git show 42fd5bd:... > ...`
или аналогичное копирование из старой ветки. Именно такая команда в журнале
DeepSeek (tool/call seq 15907) убрала запуск сценария и вернула открытие только меню.
`tools/build.py` launcher не перезаписывает. Правки делать поверх текущего HEAD,
сохраняя `--no-debug`, `--menu-only`, сценарий по умолчанию и проверку результата.

Проверяющий harness собирается отдельно в dev-cache:
`scenario-agent/ScenarioAgent.jar`; он не встраивается в PersonalKnox.jar.
В `dev-launch.json` и `dev-scenario.json` записываются пути/хеши выбранных Java-модов
и отдельного agent JAR. Если какой-либо из них пересобрали в ходе проверки,
результат не засчитывается как OK. Новый JAR проверять повторным запуском без
`--build`, чтобы испытывать именно переданный файл, а не ещё одну пересборку.

После изменений запускать `check_dev_launch.py`, `check_dev_trust.py`,
`check_dev_scenario.py`, `check_dev_scenario_agent.py`, а также
`check_dev_scenario_lua.py` через Python с lupa.lua51, затем реальный dev-сценарий.
Не заменять эти проверки старой версией тестов ради прохождения.

Существующий launch_dev.sh дополнительно проверяет протокол Python-launcher.
Если ему подложили старый dev_launch.py без сценария, он сразу возвращает ошибку,
а не открывает меню с ложным успехом. Регрессия проверена на настоящем файле из
42fd5bd. Результат --launcher-protocol не меняет файлы и не запускает игру.

Последняя проверка свежего PersonalKnox.jar выполнена без его пересборки:
отдельный ScenarioAgent.jar, совпадение хешей обоих файлов до/после, 6 модов,
core/Lua 0.9.30, закрыты 3 окна, Knox сгенерирован и экспортирован, мир сохранён,
сценарий вернул OK/0. Запуск без аргументов и единственный --menu-only проверены
на передачу встроенных параметров; --status не останавливает игру и не собирает JAR.

## Ошибки NPC после входа в мир

В прогоне 0.9.31 обнаружен undefined `pz` в OwnNpc.lua:32: Java-методу следования
передавался nil вместо высоты игрока. Вызов исправлен; регрессию проверяет
`tools/check_own_npc_bridge.py` через Python с lupa.lua51 (проверка второго этажа).

Вход в мир больше не перекрывает ошибки цикла NPC зелёным результатом: проверка
читает текущий журнал и возвращает FAIL при Lua-исключениях PersonalKnox или
сообщениях его обработчиков `error:`. `--status` показывает `scenario_failed`.
Старые журналы другого запуска и несвязанные предупреждения vanilla не считаются
ошибкой этого сценария. Итог проверки записывается в dev-launch.json.

### Собственное тело NPC, 0.9.39

Не заменять `OwnNpcBodyType.forBase(playerClass)` на прямой конструктор `IsoPlayer`:
B42 FBO исключает точный класс игрока из прохода moving objects. Наш небольшой
подкласс генерируется и кешируется один раз через Byte Buddy, который уже входит
в ZombieBuddy. Игровые классы Java 25 не добавляются в compile-time classpath.
В результате сценария теперь есть `bodyType`, а также render/culled/alpha для
диагностики. Готовая модель сама по себе не доказывает видимость на экране.
